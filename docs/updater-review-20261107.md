## 發現與修正

| 原先問題 | 本次處理 |
|---|---|
| 還原直接使用當下選定的資料夾，沒有正常更新時的完整位置核對 | 新復原紀錄綁定原 FileSystemDirectoryHandle；還原前檢查工具識別、資料夾相同項目及隨機暫存文字檔的實際載入位置證明；舊紀錄也必須通過實際位置證明 |
| 按鈕鎖定晚於非同步授權，快速連點可能進入重複流程 | UI 與更新工作階段都在第一個 await 前鎖定；保留各工具原本的 Web Lock 名稱與後台作業鎖定 |
| 多視窗使用各自保留的 journal，可能看不到其他視窗剛寫下的中斷紀錄 | 取得更新鎖後重新讀取 IndexedDB，再決定能否更新或還原；視窗計數一致忽略 URL 查詢參數與片段 |
| 快取公告未重新驗證；查詢失敗仍可能留下可安裝的舊公告 | 快取只顯示資訊；成功查詢後才啟用安裝，按下更新時再核對固定來源公告的版本、路徑、大小與 SHA-256 |
| 原 manifest 檢查只比較 content script 網址，未完整涵蓋框架、執行環境、排除規則與網頁可存取資源 | 檢查整組存取邊界與其他 manifest 能力；需要擴權或改安全設定時停止自動更新，改由維護者安排手動安裝 |
| 還原過程有檔案失敗，仍可能繼續寫回舊版 manifest | 非 manifest 檔案未全部還原成功時，不寫回版本標記；保留原版備份供再次還原 |
| 啟動後僅依版本號決定刪除復原紀錄 | 新紀錄保存目標檔案大小與 SHA-256，重新開啟後逐檔核對成功才刪除 |
| 原版備份沒有逐檔完整性欄位 | 新紀錄保存原版大小、SHA-256、工具識別、原版本、目標版本；復原資料格式、路徑、重複與大小限制先驗證再寫入 |
| 重新開啟資訊寫入失敗，可能發生在程式檔已更新之後 | 在寫入程式檔之前保存重新開啟資訊；若最後 reload 失敗，保留完成狀態並提供重新開啟按鈕 |
| IndexedDB 首次開啟失敗可能一直沿用已拒絕的 Promise | 失敗後可重試，處理資料庫被其他視窗占用與版本變更；仍等待整筆交易完成才視為備份成功 |
| 9 份近似更新器分散維護，個別修正容易漏套 | `shared/updater/` 維護共用實作，個別差異集中在設定，建置時複製至每個工具；同步檢查防止版本漂移 |

原有的固定 GitHub 來源、HTTPS、匿名 GET、禁止轉址、下載大小限制、套件與逐檔雜湊、路徑檢查、先備份後寫入、manifest 最後寫入，都予以保留或加強。更新程式不讀取或上傳病人紀錄；重新開啟所需的 Portal 連接資訊僅存本機。

## 保留的操作與相容性

- 工具各自獨立安裝，資料庫名稱、版本、資料表及原有 key 不變；不要求重新登記電腦。
- 沿用既有安裝資料夾授權、舊路徑搜尋及原工具的重新開啟資訊。
- 保留啟動檢查與開啟期間每 6 小時檢查；找到新版時等待使用者完成輸入或其他對話視窗，同一次開啟只自動提醒一次。
- 更新不擴大原有權限，原本的病人處理、貼片登記、列印、Portal 橋接、藥歷整理與後台管理程式逐檔比對保持不變。
- 雲端藥歷既有的三個中文說明檔名例外保留；其他路徑限制未放寬。
- 仍使用原更新包格式，9 個原版更新核心都已驗證能接受此次候選包。
- 舊 journal 沒有目標雜湊，無法補造歷史驗證證據：遷移時核對已載入的 manifest 與工具識別；舊紀錄還原仍先驗證實際安裝位置。新交易才具有完整的重新開啟後逐檔核對。

## Defender 與發布前驗證

這次修正具備可測試的安全與維護價值，沒有採用混淆、加密程式碼、更改檔名躲避偵測、停用防毒或加入排除清單。尚未取得使用者電腦上被隔離檔案的原始位元組，也沒有 Microsoft 複判結果，因此不知道 Fauppod 命中的實際特徵。

建議在未含病人資料的 Windows 測試環境，保留 Defender 啟用，更新安全性情報後掃描候選 ZIP 及解壓縮資料夾，再測試實際資料夾授權、更新、還原與重新開啟。記錄偵測名稱、檔案 SHA-256、Defender 引擎／安全性情報版本與時間；若仍被攔截，保留隔離並送 Microsoft 分析。單次掃描未偵測也不能保證日後版本或院內政策不會攔截。

SHA-256 用於比對資料完整性，不等於獨立發布者簽章。目前來源信任仍依賴固定 GitHub 儲存庫與 HTTPS，無法防止儲存庫發布權遭接管後，攻擊者同時更換公告與套件。若日後導入發布簽章，需要另外安排私鑰管理、金鑰輪替與原版安裝遷移；本次沒有假裝既有雜湊已提供該保護。

## 後續維護

1. 修改 `shared/updater/` 的共用模組。請勿只修改某一工具的複本。
2. 個別工具識別、資料庫名稱、重新開啟方式、中文檔名例外與發布檔案清單集中在 `scripts/updater-tools.json`。既有資料庫名稱與識別不要更換。
3. 執行 `node scripts/sync-updaters.mjs`，再以 `--check` 確認同步。
4. 執行 `node --test tests/updater-hardening.mjs`。瀏覽器測試為 `node tests/updater-browser-checks.cjs`，需要 Playwright 與 Chromium；可透過 `QA_CHROMIUM_PATH` 指定測試瀏覽器。
5. 更新各工具 manifest 版本後，執行 `node scripts/build-updater-release.mjs --all`，再執行 `node tests/updater-release-checks.mjs`。個別工具原本的建置指令已改為呼叫同一個建置器。
6. 建置只讀明列的原始碼檔案，不遞迴收集使用者資料。新增檔案要同步更新明列清單；仍遵守原版最多 80 個檔案、總原始碼 6 MiB 的相容限制。藥車標籤候選版已用 77 個名額，新增較多檔案前需安排相容升級。
7. 發布前跑原有功能測試，完成 Windows 驗證並核對原始碼、更新 JSON、ZIP 三者一致。若 main 同時有其他改版，先合併最新版並重新檢查，不可覆蓋其他工具的新功能。

舊版核心只存在於歷史更新包，測試會讀取它來驗證相容性。請勿重寫歷史版本來讓檢查通過。
